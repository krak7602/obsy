# Build obsy on versioned files and three-way merges

> **Status (2026-10-19):** research record, not the current design. Keep it as evidence; do not update it to match later design changes. The project was renamed from the working name "obsync" to **obsy**. The current design starts at [Architecture](../architecture.md). It changes one central decision: commits are ordered by conditional creates in the bucket itself, so any S3-compatible storage with conditional writes works without a server, and the Cloudflare Durable Object described below becomes an optional relay for push and device tokens ([decision](../decisions/2026-10-19-bucket-as-sequencer.md)). The merge, conflict, platform, agent, and security findings below still apply. Detailed notes are in [research-notes/](research-notes/).

Obsy should be a **file-level, server-sequenced sync system**. Its parts are one SQLite-backed Durable Object per vault as the only version authority, immutable content-addressed blobs in R2, a deterministic line-level three-way merge that knows about Markdown structure, and visible conflict copies when the merge cannot be clean. It should not be a CRDT-first system. The deciding evidence is that a CRDT kept in step with plain files must "diff in" every outside change, and in a local test two Yjs replicas that received the same external edit kept the edited line **twice**. A base-aware `git merge-file` merged the same case once. Shipping products have moved the same way: Obsidian Sync admits that its diff-match-patch auto-merge "may sometimes create duplicate text" and added a conflict-file mode in 1.9.7, and Self-hosted LiveSync now auto-merges only when a real shared ancestor exists ([Obsidian Help](https://obsidian.md/help/sync/troubleshoot); [LiveSync conflict spec](https://github.com/vrtmrz/obsidian-livesync/blob/main/docs/specs_conflict_resolution.md)). The Obsidian plugin platform rules out background sync on iOS. Sync must therefore run on launch, on foreground return, and on save, and it must survive being killed mid-write. Cloudflare's building blocks fit closely: a single-threaded DO gives a gap-free change cursor and compare-and-swap commits, and output gates mean no acknowledgement is sent before the write is durable. The marginal cost at personal scale is about **$0/month** on top of the existing $5 Workers Paid plan. A server-side AI agent conflicts directly with end-to-end encryption. Version 1 should therefore be honestly server-trusted, and the agent should write only through narrow, anchored, compare-and-swap operations with recorded provenance, never through whole-file overwrites.

## Three-way merge beats CRDTs for notes edited outside the editor

The core design question is which merge primitive keeps offline-edited plain Markdown safe. The obsy workload is snapshot-based: a phone edits a note offline for hours, Obsidian rewrites links on rename, Templater creates files, and a server-side agent writes check-ins into the daily note. The sync engine sees before-and-after files, not keystrokes. That fact decides most of the argument.

**The CRDT field is mature, but its maturity does not fix the plain-file problem.** In late 2026 there are three maintained MIT options. Yjs 13.6.33 is pure JavaScript and about 20 KB min+gz in older benchmarks. Loro 1.16.4 has a stable 1.x format, a Fugue-based text CRDT, Eg-walker-derived storage, and shallow snapshots. Automerge 3.5.0 cut memory "by over 10x" relative to v2; one Moby Dick paste dropped from about 700 MB to about 1.3 MB ([Yjs](https://github.com/yjs/yjs); [Loro 1.0](https://loro.dev/blog/v1.0); [Automerge 3](https://automerge.org/blog/automerge-3/)). The research front moved too. Eg-walker (EuroSys 2025) uses an order of magnitude less steady-state memory than earlier CRDTs and merges long offline branches orders of magnitude faster than OT. FugueMax (IEEE TPDS, November 2025) achieves "maximal non-interleaving" of concurrent inserts ([arXiv 2409.14252](https://arxiv.org/abs/2409.14252); [Kleppmann 2025](https://martin.kleppmann.com/2025/11/01/fugue-minimizing-interleaving.html)). Avoid two libraries: json-joy switched to **AGPL-3.0-only at v18**, and the Diamond Types JS package has not been updated since 2023 ([json-joy npm](https://npmjs.com/package/json-joy); [diamond-types](https://github.com/josephg/diamond-types)). On a phone, Loro and Automerge each ship about **1.1 MB gzipped of WASM** ([unpkg loro-crdt](https://unpkg.com/loro-crdt@1.16.4/web/loro_wasm_bg.wasm); [unpkg automerge](https://unpkg.com/@automerge/automerge@3.5.0/dist/automerge.wasm)).

The problem is diff-in. Yjs has no `setText`, so any change made outside the CRDT must be turned into insert and delete operations by diffing the old CRDT text against the new file ([discuss.yjs.dev #2461](https://discuss.yjs.dev/t/does-a-huge-text-with-tiny-changes-overriding-lead-an-entire-document-sync/2461)). Loro (`LoroText.update`, plus a coarser `updateByLine` for texts over about 50,000 characters) and Automerge (`updateText`) build this diff step in ([Loro typings](https://unpkg.com/loro-crdt@latest/web/loro_wasm.d.ts); [Automerge text docs](https://automerge.org/docs/reference/documents/text/)). Merge quality is then capped by a two-way diff that cannot know where the user's cursor really was ([discuss.yjs.dev #2358](https://discuss.yjs.dev/t/plain-text-input-component-with-y-text/2358)). The worse failure is duplication. CRDTs preserve every concurrent insert by design ([Automerge conflicts](https://automerge.org/docs/reference/documents/conflicts/)). A file can reach a device by more than one path: obsy, an agent write, or a stray iCloud copy. If two replicas each diff the same external change in, the CRDT sees two inserts and keeps both. A small local test for this research reproduced that with `yjs` 13.6.33: two replicas each appended the identical `- pay rent` line and, after exchanging updates, held it twice ([yjs](https://github.com/yjs/yjs)). CRDTs also never surface conflicts. With an agent writing in the same files, a merged note that is wrong without any warning is a worse outcome than a visible conflict.

**Three-way merge has the property obsy needs most: identical concurrent edits are idempotent.** In the same local test, `git merge-file` merged two identical appends into one line. Applying a diff-match-patch patch on top, which is how Obsidian Sync merges, produced the line **twice** ([git-merge-file](https://www.kernel.org/pub/software/scm/git/docs/git-merge-file.html); [@sanity/diff-match-patch](https://www.npmjs.com/package/@sanity/diff-match-patch)). The test also showed plain diff3's weakness. When the agent and the user append *different* lines at the same place, which is the most common obsy case, `git merge-file --diff3` and `node-diff3` both report a conflict. Only `--union` and diff-match-patch keep both lines ([node-diff3](https://github.com/bhousel/node-diff3)). The fix is a small Markdown-aware layer on top of line diff3. This layer parses YAML frontmatter separately and merges it key by key (never put conflict markers inside YAML). It treats list items and headings as units, and it auto-resolves "both sides inserted different lines at the same anchor and deleted nothing" by concatenating in a fixed order, such as server arrival order. Every other overlapping region becomes a visible conflict. The other serious position deserves a fair hearing. The reconcile-text project argues for word-level tokens and says that "a slightly imperfect sentence is usually better than conflict markers". It also documents that git's union driver can duplicate whole lines and that diff-match-patch "failed patches can lose edits" ([reconcile-text](https://schmelczer.dev/articles/reconcile-text-3-way-merge/)). A word-level pass is worth trying as a second step inside a single conflicting line, accepted only if it is clean. Line-level stays the primary unit because Markdown is line-oriented and line-level conflicts are easy to read.

**Operational transformation and AI merge tools change nothing yet.** OT needs operations captured inside an editor session and is slow on long offline branches ([arXiv 2409.14252](https://arxiv.org/abs/2409.14252)). Mergiraf, the main structured merge driver, lists JSON, YAML, TOML, and HTML but **not Markdown** ([Mergiraf languages](https://mergiraf.org/languages.html)). LLM-assisted merge is still at RFC stage, for example LLMinus for the Linux kernel in January 2026 ([LWN](https://lwn.net/Articles/1053714/)). For obsy, the LLM's correct role is to *suggest* a resolution for a conflict that has already been surfaced, while the deterministic diff3 output and both inputs stay on record. No Markdown-aware merge library exists, so obsy must build this layer, a modest amount of work on top of `node-diff3` (MIT). Git can serve as a test oracle but not as a runtime dependency.

## The landscape converged on file revisions with visible conflicts

Every serious Obsidian sync product falls into one of two families. The first is file or revision sync with an ancestor-aware merge or conflict copies. The second is Yjs-based live collaboration. Their histories show what goes wrong.

| Project | Architecture | License | Status (Oct 2026) | What obsy takes |
|---|---|---|---|---|
| Obsidian Sync | Proprietary; diff-match-patch for `.md`, last-modified-wins for other files, AES-256-GCM E2EE | Proprietary; `obsidian-headless` is UNLICENSED | Active; headless CLI 0.0.14 | Conflict-file naming, per-category config sync, pull-only and mirror modes for headless clients |
| Self-hosted LiveSync | PouchDB to CouchDB, or journal "packs" on object storage; content-addressed chunks; revision trees | MIT | Very active; 1.0.38 on 2026-10-17 | Ancestor-only merge, byte-based "known content", per-device displayed-revision provenance, deletion revalidation |
| Remotely Save | Stateless remote; 4x4 decision table from local, remote, and last-sync listings | Apache-2.0 `src/`; **PolyForm Strict `pro/`** | Unmaintained since 0.5.25 (2024-10-20) | V3 design doc (Apache) and mass-change abort threshold |
| Relay | Yjs per document; y-sweet-fork server persisting to R2; attachments as blobs | MIT plugin and server; proprietary control plane | Active; 0.8.12 | The "CRDT for Markdown, blobs for attachments" split; its 2026 bug list |
| YAOS | One DO and one vault-wide Y.Doc per vault; checkpoint plus journal in DO SQLite; R2 blobs | Not checked | Active | Closest Cloudflare prior art and its memory ceiling |
| Fast Note Sync | Go server; real-time sync; REST and MCP | Apache-2.0 | Active | Evidence that MCP-style agent access is in demand |
| Peerdraft, Obsidian Decentralized | Yjs over WebRTC; P2P LAN | GPL-3.0 | Active | Ideas only |
| Syncthing, iCloud, Git | Version vectors with conflict copies; OS sync; line merge | Varies | Mature | Tombstones, NFC paths, temp-file-then-rename writes |

Sources: [Obsidian Sync](https://obsidian.md/help/sync/troubleshoot), [obsidian-headless](https://github.com/obsidianmd/obsidian-headless), [LiveSync](https://github.com/vrtmrz/obsidian-livesync), [LiveSync journal design](https://github.com/vrtmrz/obsidian-livesync/blob/main/docs/design_docs_of_journalsync.md), [Remotely Save LICENSE](https://github.com/remotely-save/remotely-save/blob/master/LICENSE), [Relay](https://github.com/No-Instructions/Relay), [relay-server](https://github.com/No-Instructions/relay-server), [YAOS architecture](https://raw.githubusercontent.com/kavinsood/yaos/main/docs/architecture.md), [Fast Note Sync](https://github.com/haierkeys/obsidian-fast-note-sync), [Peerdraft](https://github.com/peerdraft/obsidian-plugin), [Syncthing](https://docs.syncthing.net/users/syncing).

**LiveSync's 1.0 conflict rules are the most useful public specification to learn from.** They decide whether content is already known by "file bytes, rather than path, size, modification time, or revision generation". Missing or compacted history "stops conservative automatic merge instead of guessing a base". Two devices that create the same path with different bytes produce two versions for manual choice, not an empty-base merge ([LiveSync conflict spec](https://github.com/vrtmrz/obsidian-livesync/blob/main/docs/specs_conflict_resolution.md)). Its journal sync, which keeps a per-client cursor, receives before it sends, and downloads timestamped packs, needs only put, get, and list ([journal design](https://github.com/vrtmrz/obsidian-livesync/blob/main/docs/design_docs_of_journalsync.md)). Obsy replaces CouchDB revision trees with something simpler: one sequencer in a DO.

**The failure reports converge on six causes.** These are: deletes inferred from absence; mtime and clock-skew decisions; Unicode NFC/NFD and case collisions; races with Obsidian's rename "update links" prompt; partial uploads marked as synced; and two sync systems running on one vault. Obsidian Sync users report deleted folders that come back and notes that vanish ([forum](https://forum.obsidian.md/t/obsidian-sync-repeatedly-restoring-deleted-files/81711/6)). LiveSync issue #1259 reports NFD-named files invisible on iOS. Relay 0.8.12 left a 0-byte file marked "Synced" (#137), and answering a rename-driven "Update links" prompt deleted a note (#136) ([LiveSync issues](https://github.com/vrtmrz/obsidian-livesync/issues?q=is%3Aissue); [Relay #136](https://github.com/No-Instructions/Relay/issues/136)). Remotely Save has open "deleted files come back" bugs ([#985](https://github.com/remotely-save/remotely-save/issues/985)). In 2026 both LiveSync and Relay added explicit guards against republishing remotely deleted files. That confirms the lesson: **absence is never a delete without a recorded base.** None of these products documents an AI agent writing server-side into a synced vault, so obsy's agent integration has no direct precedent.

### What obsy may legally reuse

This section is engineering guidance, not legal advice. MIT and Apache-2.0 code may be reused with its notices. That covers LiveSync, the Relay plugin and server (keep the y-sweet and y-crdt MIT notices), Obsidian Git, Fast Note Sync, Remotely Sync, and Remotely Save's Apache-licensed `src/`, `docs/`, and pre-split tree ([relay-server LICENSE](https://github.com/No-Instructions/relay-server/blob/main/LICENSE)). **Remotely Save's sync engine now lives in `pro/` under PolyForm Strict 1.0.0.** The free build itself imports `syncer` from `../pro/src/sync`, and the license binds its terms "as both strict obligations and conditions" ([remotely-save pro/src](https://github.com/remotely-save/remotely-save/tree/master/pro/src); [PolyForm Strict](https://polyformproject.org/licenses/strict/1.0.0/)). The clean route is to learn only from the Apache V3 design document, which credits MIT tools (syncrclone, rsinc, rclone bisync), and from `src/sync.ts` at commit `0802767` (2024-05-25), which predates the split and was Apache-licensed throughout ([V3 design](https://github.com/remotely-save/remotely-save/blob/master/docs/sync_algorithm/v3/design.md); [sync.ts @0802767](https://github.com/remotely-save/remotely-save/blob/08027677267934d3a1ca6f6e3cf06ee1be53ee52/src/sync.ts)). Do not read current `pro/src/sync.ts` or `conflictLogic.ts`. Do not take code from BYOC: its MIT `src/` file names mirror upstream `pro/src`. That was observed but not diffed, so it is a possible licensing problem ([BYOC](https://github.com/winters27/obsidian-byoc)). Copying from Peerdraft or Obsidian Decentralized would make obsy GPL-3.0. Relay's self-hosted server is MIT, yet its README says use with more than three collaborators "requires a paid license". That does not affect a single owner but should be noted ([relay-server](https://github.com/No-Instructions/relay-server)). Two smaller points remain. The license of `@vrtmrz/livesync-commonlib`, where LiveSync's core logic lives, was not checked. **The name "obsync" is already taken** by an MIT project with a similar stack, "Cloudflare Workers + Obsidian Plugin" ([less1001/obsync](https://github.com/less1001/obsync)). This matters only if obsy is published.

## iOS gives a plugin foreground time only and buffered HTTP

**On iOS, a plugin runs only while Obsidian is in the foreground.** Obsidian Mobile is a Capacitor WebView app. Node and Electron APIs are unavailable, no public API gives background execution, and `workspace.on('quit')` is "Not guaranteed to actually run" ([obsidian.d.ts](https://github.com/obsidianmd/obsidian-api/blob/master/obsidian.d.ts); [mobile docs](https://docs.obsidian.md/Plugins/Getting+started/Mobile+development)). Apple's own engineers say that networking stops once an app is suspended ([Apple forums](https://developer.apple.com/forums/thread/750136)). A 2025 user report describes iOS quick notes lost when the phone is locked before Sync finishes ([forum](https://forum.obsidian.md/t/make-obsidian-sync-work-in-background-on-mobile/25906/100)). Mature plugins use `visibilitychange` as the real pause and resume hook. On hide, LiveSync commits pending events and suspends replication. On show, it tears down a channel that may be "stalled-but-not-terminated" and gates background replication off on mobile. Relay disables `online`/`offline` monitoring on iOS altogether ([LiveSync events module](https://github.com/vrtmrz/obsidian-livesync/blob/6412dd6d6bad877b98d1aa61690698a4a50f6c87/src/modules/essentialObsidian/ModuleObsidianEvents.ts); [Relay main.ts](https://github.com/No-Instructions/Relay/blob/f0a137da1e02efd3ae39b726344cdefe1d65efb7/src/main.ts)). The design consequences are as follows. Sync on launch (after `onLayoutReady`, because `create` fires for every file at load), on foreground return, on save, and on a timer while visible. Journal each operation before acting on it. Assume that sockets and timers died without an error.

**Networking means `requestUrl` for HTTP and a WebSocket used only as a doorbell.** `requestUrl` avoids CORS on every platform and accepts `string | ArrayBuffer` bodies and custom headers. It has **no timeout, abort, progress, or streaming**, and it buffers the whole response ([obsidian.d.ts](https://github.com/obsidianmd/obsidian-api/blob/master/obsidian.d.ts); [streaming request](https://forum.obsidian.md/t/support-streaming-the-request-and-requesturl-response-body/87381)). Wrap each call in a client-side race timer and keep each request bounded in size. Plain `fetch` and WebSocket handshakes come from `capacitor://localhost` on iOS, `http://localhost` on Android, and `app://obsidian.md` on desktop, so the Worker must allow those origins ([Ionic CORS](https://ionicframework.com/docs/faq/cors)). Relay's provider shows a working iOS socket pattern: reconnect after 30 s of silence, with jittered backoff from 300 ms to 30 s ([Relay provider](https://github.com/No-Instructions/Relay/blob/f0a137da1e02efd3ae39b726344cdefe1d65efb7/src/client/provider.ts)).

**Vault events are hints, and a reconciliation scan is the truth.** Use `Vault` for indexed files and `vault.adapter` for `configDir` and other dot-paths, which emit no events. Never hard-code `.obsidian` ([plugin guidelines](https://docs.obsidian.md/Plugins/Releasing/Plugin+guidelines)). `normalizePath` applies NFC, but files on disk can be NFD. In 1.13.5 and 1.13.6, editing an NFD-named note on macOS removed it from the index; a fix was promised for 1.13.7 ([forum bug](https://forum.obsidian.md/t/macos-notes-with-nfd-normalized-filenames-disappear-from-file-explorer-and-search-when-edited-regression-in-1-13-5-1-13-6-watcher-existence-check-compares-raw-nfd-event-name-against-nfc-normalized-listing/117189)). macOS APFS is case-insensitive by default and iOS is case-sensitive, though that source is from 2017 ([Eclectic Light](https://eclecticlight.co/2017/04/05/file-problems-in-ios-10-3-and-macos-10-13-whats-in-a-name/)). Therefore the sync key is NFC plus case-folding, the on-disk name is stored separately, and case-only renames go through a temporary name. Write with `DataWriteOptions.mtime` set from remote metadata, and keep an own-write suppression set keyed by path and hash, so that obsy's own writes do not echo back as edits.

**Remote changes must never use `vault.modify` on a note the user is typing in.** Obsidian has auto-merged disk changes into unsaved buffers since 0.11.6 (a 2-second window in 2021), and users report silent data loss from it ([changelog 0.11.6](https://obsidian.md/changelog/2021-03-09-desktop-v0.11.6/); [forum](https://forum.obsidian.md/t/editor-add-a-toggle-to-disable-automatic-merging-of-changes-non-obsidian-sync/14874/)). The guidelines say to use the Editor for the active note and `Vault.process` for other files ([plugin guidelines](https://docs.obsidian.md/Plugins/Releasing/Plugin+guidelines)). Obsy should find open `MarkdownView` leaves for the path, treating deferred tabs (since 1.7.2) as not open. For an open note, it runs the same three-way merge against `editor.getValue()` and applies minimal `editor.transaction` changes. For any other note, it merges inside `vault.process`. The platform exposes no "dirty buffer" flag, so outbound uploads should wait more than 2 s after the last edit and read with `vault.read`. `.base` and `.canvas` files are edited in custom views and need the `vault.process` path.

**Resources and secrets set firm limits.** Mobile reads whole files into memory. Plugins report trouble at about **50 MB per file**, an iOS crash loop near 35k files, and an Android `writeBinary` of 50 MB that never resolved ([Remotely Save README](https://raw.githubusercontent.com/remotely-save/remotely-save/master/README.md); [forum](https://forum.obsidian.md/t/ios-obsidian-app-crash-loop-once-passing-30k-files/109666); [forum](https://forum.obsidian.md/t/obsidian-mobile-android-adapter-writebinary-on-large-files-never-resolves-and-repeatedly-appends-data/108554)). Cap attachments on mobile, process large files one at a time, and write downloads in pieces with `appendBinary` (1.12.3). Keep the sync index in IndexedDB, as Remotely Save does with localforage, not in `data.json`. That file is rewritten whole, stored in plaintext, and copied by other sync tools ([remotely-save localdb.ts](https://github.com/remotely-save/remotely-save/blob/34db181af002f8d71ea0a87e7965abc57b294914/src/localdb.ts)). Device tokens belong in `app.secretStorage` (1.11.4), which the official guide describes as "local storage, keyed to the specific vault" ([secret storage guide](https://docs.obsidian.md/plugins/guides/secret-storage)). A 2026-08-29 report says same-named secrets are **shared across vaults on mobile**, so use a vault-unique ID such as `obsy-<vaultRandomId>` ([forum](https://forum.obsidian.md/t/secretstorage-appears-to-be-shared-across-vaults-on-mobile-but-vault-scoped-on-desktop/117793)). A realistic `minAppVersion` is 1.12.3.

**Distribution has new rules.** Since May 2026 the Community directory scans every version automatically and plans to require capability declarations ("network, file system, clipboard") ([Obsidian blog](https://obsidian.md/blog/future-of-plugins/)). Policies ban client-side telemetry, obfuscation, and self-updating, and require README disclosure of network use and accounts ([developer policies](https://docs.obsidian.md/Community+directory/Developer+policies)). For a personal system, BRAT installs from GitHub releases on both macOS and iOS and accepts a read-only token for private repositories ([BRAT](https://raw.githubusercontent.com/TfTHacker/obsidian42-brat/main/README.md)). Downloading WASM at runtime would violate the no-remote-code rule. This is one more reason to keep the plugin pure JavaScript.

## One Durable Object per vault, with R2 blobs, costs almost nothing

**A SQLite-backed Durable Object is the right version authority.** It is single-threaded. `transactionSync` makes compare-and-swap atomic, and output gates hold outgoing messages "until all previous writes have been confirmed", so a device or agent never receives an acknowledgement for a commit that was lost ([DO SQLite API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)). It includes **30-day point-in-time recovery** through bookmarks, and every restore returns a bookmark that can undo it. It also provides one alarm per object, which can be delayed by up to a minute ([DO SQLite API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)). These are the binding limits:

| Limit | Value | Design consequence |
|---|---|---|
| DO storage per object | 10 GB (same page's FAQ says 1 GB on Free) | Metadata only; trivially sufficient |
| Row / BLOB / string | **2 MB** | File bodies go to R2, not to DO rows |
| SQL statement | 100 KB; 100 bound parameters | Batch manifest queries |
| Isolate memory | 128 MB | No vault-wide in-memory Y.Doc |
| CPU per request | 30 s default, up to 5 min | Bound merge size; big diffs are rare |
| Throughput | ~1,000 req/s soft per object | Irrelevant at 3 writers |
| Hibernating WebSockets | 32,768 per DO; 16 KiB attachment | One socket per device; cursor in the attachment |
| R2 same-key writes | **1 per second** | Content-addressed keys avoid hot keys |
| R2 versioning | **Not implemented** (S3 table) | History is application-built |
| R2 presigned URLs | ≤ 7 days, S3 domain only, no POST | Use for large attachments only |
| Worker request body | 100 MB (Pro) | Chunk or presign large files |

Sources: [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/), [DO State API](https://developers.cloudflare.com/durable-objects/api/state/), [DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/), [R2 limits](https://developers.cloudflare.com/r2/platform/limits/), [R2 S3 compatibility](https://developers.cloudflare.com/r2/api/s3/api/), [R2 presigned URLs](https://developers.cloudflare.com/r2/api/s3/presigned-urls/), [Workers limits](https://developers.cloudflare.com/workers/platform/limits/).

**R2 is strongly consistent and supports atomic conditional PUTs, but has no object versioning.** Read-after-write, list, and delete are strongly consistent. With `If-None-Match: *` on an absent key, "at most one request succeeds" ([R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/)). The Workers binding exposes `onlyIf` and accepts a `sha256` checksum on `put` ([R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)). Some 2026 third-party blogs claim R2 supports versioning. The official S3 table marks `Get/PutBucketVersioning` as unimplemented, and staff call it "on our roadmap" ([R2 S3 API](https://developers.cloudflare.com/r2/api/s3/api/); [Discord](https://www.answeroverflow.com/m/1445118038889205820?focus=1445118038889205820)). The resulting pattern is immutable `blobs/sha256/<hex>` objects written with if-absent semantics, referenced from the DO's revision table. Lifecycle rules cannot express "unreferenced", so garbage collection must be driven by the application ([R2 lifecycles](https://developers.cloudflare.com/r2/buckets/object-lifecycles/)). PITR covers only the DO. Blob retention must therefore be at least as long as the 30-day metadata window, and a GC bug is the main route to permanent history loss.

**The hibernation API makes an always-on push channel almost free.** With `ctx.acceptWebSocket`, idle objects "are not billed for duration". Incoming messages bill at 20:1, outgoing messages are free, and `setWebSocketAutoResponse` answers pings without waking the object ([DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/); [DO State API](https://developers.cloudflare.com/durable-objects/api/state/)). One constraint matters for an agent that runs in its own Worker: **"Deploying a new version restarts every Durable Object and disconnects existing WebSockets"** ([DO WebSockets](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)). If the vault DO lives in the agent's Worker, every agent deploy drops every device. A separate obsy Worker, reached from the agent through a service binding, isolates that effect. Service binding calls add no request fees, and a named `WorkerEntrypoint` can expose only the methods the agent needs ([Workers RPC](https://developers.cloudflare.com/workers/runtime-apis/bindings/service-bindings/rpc/); [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)).

**YAOS shows both the appeal and the ceiling of a CRDT-on-DO design.** It keeps one DO and one vault-wide Y.Doc, persists a chunked checkpoint plus a journal compacted at more than 50 entries or 1 MB, and refuses service rather than serving an empty vault when storage is corrupt. It names a memory ceiling of about 117 bytes per unmergeable Yjs struct, resident in the 128 MB isolate, and keeps tombstone metadata forever ([YAOS architecture](https://raw.githubusercontent.com/kavinsood/yaos/main/docs/architecture.md)). Obsy keeps YAOS's good ideas: per-vault ordering, integrity hashes, and refusing to serve on corruption. It avoids the ceiling by keeping bodies out of DO memory.

**The cost is a rounding error.** Assume 300 edits a day, 3 devices, 5,000 files, and 1–2 GB. Every dimension then stays inside included allowances: 1M DO requests, 400,000 GB-s (a DO awake all month uses about 324,000), 50M SQLite rows written, and R2's 10 GB-month and 1M Class A operations free tier. History of 20 GB adds **$0.15/month** ([DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/); [R2 pricing](https://developers.cloudflare.com/r2/pricing/)). This estimate is arithmetic on published prices, not a measurement. Two cautions apply. The allowances are account-wide and shared with other projects on the same account, and the bill rises only with an anti-pattern: non-hibernating sockets across many DOs (Cloudflare's own example reaches about $419/month), or one SQLite row per keystroke.

## The protocol: compare-and-swap commits, one sequenced feed, and tombstones that edits can beat

### Versioning and identity

**A central sequencer makes version vectors unnecessary.** Figma rejected CRDTs because its "server is the central authority" ([Figma](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)). Syncthing needs version vectors only because it has no such authority ([BEP v1](https://docs.syncthing.net/specs/bep-v1.html)). Linear reportedly uses a database-wide `lastSyncId` ([reverse-linear-sync-engine](https://github.com/Aslam97/reverse-linear-sync-engine)). Obsy should assign a vault-wide integer `seq` to every committed revision and use "the `seq` at which this file last changed" as its `rev`. Every write carries `base_rev`. The DO accepts a write only if `base_rev == head_rev`; otherwise it merges or reports a conflict. Wall clocks (mtime, HLC) are informational and serve only as tie-breakers for binary files. For identity, use **stable file IDs with path as an attribute**, and make rename a first-class atomic operation. Dropbox's Nucleus rewrite gave files stable identifiers because the delete-plus-add model left files missing when one half was lost ([Dropbox](https://dropbox.tech/infrastructure/rewriting-the-heart-of-our-sync-engine)). Obsidian's link-updating renames (Relay #136) make move-plus-edit races routine. Clients generate IDs at creation so that creating a file works offline, as in Figma. The client's local state maps paths to IDs.

### Client state and change detection

The client keeps Dropbox's three trees ([Dropbox testing post](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine)). The remote tree is the server manifest at cursor N. The local tree is the last observed disk state. The **synced tree** is the per-file merge base: `server_rev`, `content_hash`, `size`, `mtime`, and for Markdown the base text itself, so the client can run a three-way merge offline. A durable outbound journal of operations keyed by client `op_id` completes the state. Use `{size, mtime}` only to prove that a file is unchanged. Hash anything whose mtime falls inside the scan's timestamp resolution, because of the racy-git problem: same mtime, different bytes ([racy-git](https://git-scm.com/docs/racy-git)). This follows Unison, where update detection "considers only the contents" ([Unison manual](https://raw.githubusercontent.com/bcpierce00/unison/master/doc/unison-manual.tex)). Write downloads to a temporary file and rename it into place, as Syncthing does ([Syncthing](https://docs.syncthing.net/users/syncing.html)).

### Commits, merge, and the change feed

Uploads have two phases, which makes retries safe. **Phase one** stores bytes at `blobs/sha256/<hex>`. Markdown and small files go through the Worker, which hashes the body and writes it with if-absent semantics. Large attachments go up in bounded chunks or to a presigned staging key, followed by verification. **Phase two** sends `commit {op_id, file_id, path, base_rev, hash, size, kind}` to the DO. In one `transactionSync` call, the DO does the following. It returns the stored result if it has already seen the `op_id`. It acknowledges a no-op if `hash == head_hash`, which removes echo writes and identical edits. It fast-forwards if `base_rev == head_rev`. Otherwise it merges. The merge needs the base and head blobs from R2, and that fetch is an `await` during which other requests can interleave. The DO therefore reads, fetches, merges, and then re-checks `head_rev` inside a final `transactionSync`, retrying if the head moved. A clean merge becomes a new revision with two parents and `auto-merged` provenance, and the response returns the merged hash so the client can apply it locally through the editor-safe path. The client uses the same three-way merge function, shipped as one shared TypeScript package, so that typing done after the upload is not lost.

The **change feed** is `GET /changes?since=<seq>&epoch=<epoch>`. It returns ordered `{seq, file_id, path, rev, hash, deleted, size, actor, ts}` entries, and the client advances its cursor only after it has durably applied them. The vault `epoch` works like Syncthing's Index ID. After any PITR restore or reset, the server bumps it, which forces every client into a full hash reconciliation instead of trusting a stale cursor ([BEP v1](https://docs.syncthing.net/specs/bep-v1.html)). The hibernating WebSocket carries only `{"type":"changed","seq":N}` plus presence. Losing a push does no harm. Each sync cycle **receives before it sends**, following LiveSync's journal rule. The result is effectively-once application on top of at-least-once delivery.

### Deletes, renames, and joining devices

A delete is a tombstone revision and is subject to the same compare-and-swap. **A delete whose `base_rev` is not current is rejected, and an edit against a tombstone resurrects the file.** Edit beats delete, which is Syncthing's data-safe choice ([Syncthing](https://docs.syncthing.net/users/syncing.html)). The server expands a folder delete into per-child tombstones, each checked by compare-and-swap, so a child the deleting device never saw survives. Clients apply remote deletes through Obsidian's trash, not hard deletes. Tombstones must outlive the longest offline window allowed (for example 180 days). A client whose cursor predates the GC horizon must reconcile fully, and must ask before uploading "new" files whose hashes match tombstones. That check is the guard against resurrection.

**A joining device has no merge base, so it must never infer a delete.** Unison treats missing archives as "both completely empty" and marks differing files as conflicts ([Unison manual](https://raw.githubusercontent.com/bcpierce00/unison/master/doc/unison-manual.tex)). The join procedure follows from that. Identical hashes adopt the server revision. Local-only files upload. Server-only files download. Same path with different bytes becomes a conflict copy. Deletes start to propagate only after join completes. Hard rails sit on top: rclone-style abort when a batch would delete more than a threshold (rclone defaults to 50%), and a sentinel and vault-ID check so that an empty or unmounted folder never reads as "the user deleted everything" ([rclone bisync](https://rclone.org/bisync/)). Remotely Save's "files ≥ 50% modified" guard is the same idea ([V3 intro](https://github.com/remotely-save/remotely-save/blob/master/docs/sync_algorithm/v3/intro.md)). Creation races get special handling, because a daily note created on the phone and by the agent has no common ancestor. Obsidian Sync simply keeps the remote copy ([Obsidian Help](https://obsidian.md/help/sync/troubleshoot)). Obsy should adopt LiveSync's rule: accept without conflict only when one version "clearly extends" the other ([LiveSync 0.25.80](https://newreleases.io/project/github/vrtmrz/obsidian-livesync/release/0.25.80)), and otherwise produce a conflict copy.

### Conflicts, configuration, and binaries

When the Markdown merge is not clean, the head stays at the path. The losing side becomes `Note (conflict <device> <YYYYMMDDHHMM>).md`, close to Obsidian's familiar `(Conflicted copy device-name ...)` form, plus a conflict record that the plugin shows with a diff ([Obsidian Help](https://obsidian.md/help/sync/troubleshoot)). Frontmatter merges key by key. Binary and canvas files get conflict copies, never silent last-writer-wins. The config folder is opt-in per category. `workspace*.json` and obsy's own `data.json` are always excluded, and the agent never writes to the config folder ([Obsidian Sync settings](https://obsidian.md/help/sync/settings); [Obsidian Git tips](https://github.com/Vinzent03/obsidian-git/blob/master/docs/Tips-and-Tricks.md)).

### Encryption with a server-side agent

**End-to-end encryption and a server-side agent that reads notes cannot both hold for the same content.** If the server holds a key that can decrypt the notes, the system "is not end-to-end encrypted any more" ([Calmara](https://calmara.app/blog/why-ai-note-apps-arent-end-to-end-encrypted)). Obsidian Sync's "Standard" mode, where Obsidian manages the key, is the honest name for that design. Even its E2EE mode exposes the path-to-content mapping, device identity, timing, and deterministic hashes ([Obsidian security](https://obsidian.md/help/sync/security)). E2EE would also stop server-side merging and plaintext-hash deduplication. The options are no E2EE, an agent-held key labelled as server-trusted, per-folder E2EE that the agent cannot read, or agent-to-client sealed proposals that let the agent write without reading. **Version 1 should be server-trusted**, using TLS, per-device revocable tokens, and SSE-C as an option ([R2 Workers API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/)). It should be labelled as such. Sealed E2EE folders can come later, with client-only merges and keyed HMAC hashes.

### Integrity, recovery, and testing

Every blob is verified against its SHA-256 on write and on read. Syncthing verifies blocks before writing them ([Syncthing](https://docs.syncthing.net/users/syncing.html)). Restores move **forward**: replaying the manifest at seq N writes new revisions that clients sync normally. DO PITR is the backstop for metadata corruption and is always followed by an epoch bump ([DO SQLite API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)). Three more tools complete recovery: a `verify` command that compares client hashes with the server manifest, a scheduled check that every referenced hash exists in R2, and a periodic plain-tree export to a second location, so recovery never depends on obsy itself.

Testing must be **deterministic simulation**. Dropbox's CanopyCheck and Trinity simulate the file system, network, and timers from a seed, inject crashes and reordering, minimise failing cases, and run "tens of millions" of seeds nightly ([Dropbox testing post](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine)). TigerBeetle reports that 3.3 seconds of its VOPR simulator equals 39 minutes of real-world time ([TigerBeetle VOPR](https://docs.tigerbeetle.com/about/vopr)). Write the client planner and DO commit logic as pure functions over (remote, local, synced, journal), and simulate a Mac, an iPhone, and the agent with offline periods, crashes between blob upload and commit, duplicate messages, and racy mtimes. The invariants are these: convergence when quiet; **no acknowledged human byte is ever unreachable** (it exists at a live path, in a conflict copy, or in history); no delete applies to an unseen revision; no agent commit without a matching expected revision; and replaying any journal is idempotent. Property tests cover merge identities, such as `merge(base, x, base) == x`, and path normalisation, with `git merge-file` as the merge oracle.

## The agent writes through narrow, anchored, attributable operations

**Treat the agent as a device with fewer rights than the human devices.** The adjacent evidence agrees. Ink & Switch's Patchwork bot "makes changes as another collaborator" on a branch that users can "partially or completely merge", and users found rationale comments helpful because AI tools "can also give bad suggestions" ([Ink & Switch](https://www.inkandswitch.com/patchwork/notebook/2024-version-control/07/)). Anthropic's text editor tool requires `str_replace` to match exactly one location ([Anthropic docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/text-editor-tool)). The MCP filesystem server marks `edit_file` as non-idempotent, saying it "can fail or double-apply" ([MCP filesystem](https://github.com/modelcontextprotocol/servers/tree/main/src/filesystem)). Research on multi-user documents with an AI agent found user concerns about interruption and responsibility ([arXiv 2509.11826](https://arxiv.org/pdf/2509.11826)).

The resulting design has five rules. **First, the agent calls the vault DO by RPC through a narrow `AgentEntrypoint`, never by raw file PUT.** It gets these operations. `create_if_absent(path, content)` creates new files. `append_to_section(file_id, heading_path, text, expected_rev?)` handles check-ins and additions. `replace_block(file_id, block_id, expected_block_hash, text)` replaces regions that the agent owns. `propose_patch(file_id, base_rev, diff, rationale)` covers everything else. **Whole-file overwrite of an existing human file is not offered.** Second, section and block operations re-anchor on the *current* head at commit time. If the target anchor still matches exactly once and its hash is unchanged, the operation rebases instead of failing, so it commutes with human edits elsewhere in the note. Server-side appends commute in the same way and remove most agent–user conflicts on the daily note. If the anchor is missing, ambiguous, or changed, the write becomes a proposal, never a conflict copy in the user's space. Third, agent-owned regions are fenced: `<!-- obsy:agent id=… -->` … `<!-- /obsy:agent -->`, or a callout. A human edit inside the fence transfers ownership to the human. Fourth, presence protects active editing. Devices report the focused path and last keystroke time over the socket, and the DO defers or downgrades agent writes to a "hot" note. Fifth, every revision records `actor = agent`, a run ID, and a tool-call ID. "Undo the agent's change" writes a new revision that restores exactly that revision's predecessor by compare-and-swap, and falls back to a three-way revert if humans edited the note since. The agent is rate-limited below the mass-change rails and has no delete permission on human files without explicit approval. Proposals live in a server-side inbox that the plugin renders as diffs. An LLM-suggested resolution for a real conflict is itself only a proposal.

## Recommended architecture and phased build plan

The recommended system has four parts. **The obsy Worker**, separate from the agent's Worker, holds `VaultDO` (SQLite) and an R2 bucket. `VaultDO` owns these tables: `vault(id, epoch)`, `files(file_id, path_key, display_path, kind, head_rev, head_hash, size, deleted)`, `revisions(seq PK, file_id, rev_parent, merge_parent, path, hash, size, deleted, actor, device_id, op_id, op_kind, ts)`, `ops(op_id, result)`, `devices(device_id, token_sha256, name, cursor, last_seen, revoked)`, `conflicts`, and `proposals`. The `path_key` is NFC plus case-folding. A uniqueness rule on `path_key` across live files rejects case and normalisation twins. The DO also holds hibernating sockets with device ID and cursor in the attachment, and an alarm that runs GC, integrity checks, and exports. **R2** holds `blobs/sha256/<hex>` (immutable) and `uploads/` (staging, with a lifecycle rule). **The Obsidian plugin** is pure TypeScript with `isDesktopOnly: false`. It contains a scanner, an IndexedDB state store for the three trees and the journal, the shared merge package, an editor-safe applier, SecretStorage tokens, and a `requestUrl` transport with timeouts. **The agent** reaches `AgentEntrypoint` through a service binding, so it needs no HTTP credentials; the binding is the capability. Auth uses per-device bearer tokens, stored as hashes in the DO, plus 60-second HMAC tickets for WebSockets, following YAOS ([YAOS architecture](https://raw.githubusercontent.com/kavinsood/yaos/main/docs/architecture.md)).

### Open questions and risks

Several decisions are still open. The first is the default conflict form: copies, which match Obsidian 1.9.7, or in-body diff3 markers. The second is retention windows for history, tombstones, and the maximum offline period, which must be consistent with each other. The third is whether small Markdown revisions are also stored in DO SQLite, inside the 2 MB row limit, for faster merges and PITR coverage, or whether everything goes to R2 for uniformity. The remaining questions are which folders, if any, become sealed and unreadable by the agent; whether obsy is ever published, which brings the name collision and directory review into play; which sync method the vault uses today and how to cut over from it; and whether the `requestUrl` and SecretStorage behaviour on iOS matches the documentation, because neither the HTTP stack nor the storage backing is publicly specified.

The main risks, in order, are these. (1) **History-destroying GC bugs.** R2 has no versioning, so soft-delete blobs, delay GC, and keep independent exports. (2) **Editor clobbering on open notes**, because the platform exposes no dirty flag; test the transaction path hard. (3) **Wrong ordering from union auto-merge** of concurrent appends. This is acceptable for check-ins but needs corpus evidence. (4) **iOS suspension mid-write**, mitigated by the journal-first design and idempotent commits. (5) **Unicode and case collisions** across macOS and iOS, given that Obsidian itself regressed on NFD in 2026. (6) **Agent runaway edits**, capped by rate limits, missing delete rights, and mass-change rails. (7) **Shared Cloudflare allowances and deploy coupling with the agent's Worker.** (8) **Licence contamination** from reading PolyForm or GPL code. Several facts also remain unverified: Cloudflare's per-object storage figure on Free, whether `put` rejects a mismatched `sha256`, and the WebSocket attachment size of 16 KiB versus the older 2 KiB.

## Conclusion

This research reverses the usual intuition. For an agent-plus-human vault, the hard problem is not merging concurrent keystrokes, where CRDTs shine. It is keeping provenance across snapshot-level changes that arrive from editors, renames, templates, and an LLM. That needs a single sequencer, stored bases, and refusing to guess. CRDTs answer a question obsy mostly does not ask, and their diff-in step adds the duplication bug that three-way merge removes. The Durable Object's serial execution and output gates are what make this simple: most of the version-vector, revision-tree, and journal-pack machinery that LiveSync and Syncthing need is unnecessary.

The agent is the novel part, and it shifts the design priority from merge cleverness to **write discipline**. If the agent can only append, replace fenced blocks, or propose patches, all checked by compare-and-swap and recorded with its identity, most conflicts that would need a clever merge never occur. The same discipline settles the encryption question honestly: a server-side agent means a server-trusted vault, and obsy should say so plainly rather than claim end-to-end encryption.
